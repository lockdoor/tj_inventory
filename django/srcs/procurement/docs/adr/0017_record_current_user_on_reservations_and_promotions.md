# ADR 0017: Record Current User on Stock and Arrival Reservations and Sourcing Promotions

## Status
Accepted

## Context
The system uses `AuditableMixin` to track creator, modifier, and soft-deletion metadata (`created_by`, `updated_by`, `deleted_by`) across models like `StockReservation`, `ArrivalReservation`, and `Shortage`. 

Previously, when reservations were created, updated, or released:
1. The actual requesting user context was not consistently propagated through service methods and signal handlers, often falling back to system defaults, parent model creators, or the current update user context.
2. In multi-stage sourcing promotion flows:
   - When a `Shortage` was promoted to an `ArrivalReservation`, the reservation lost the identity of the user who originally created/triggered the shortage.
   - When an `ArrivalReservation` was promoted to a physical `StockReservation` (during receiving movement completion), the physical reservation was recorded as created by the warehouse operator completing the receipt, rather than the sales rep or customer who originally booked the reservation.

This lack of consistency degraded our audit logs, making it difficult to trace who originally committed stock holds or future expected arrival commitments.

## Decision
We updated the system to explicitly track and preserve the requesting user's identity across the entire reservation lifecycle and promotion pipeline:

### 1. Propagating the Requesting User
- **Service API Updates**: Updated `ArrivalReservationService.update_reservation`, `SalesService.save_manual_allocations`, `SalesService.refresh_allocation`, and `SalesService.update_order` to explicitly accept a `user` parameter and record it as `updated_by` or `created_by` where appropriate.
- **Release and Deletion Auditing**: Modified release/cancellation paths (such as the `cleanup_sales_order_item_allocations_and_reservations` signal and `ArrivalReservationReleaseView`) to resolve and pass the operator user context, ensuring `deleted_by` is recorded when soft-deleting reservation rows.

### 2. Sourcing Promotion Creator Inheritance
- **Shortage -> Arrival Reservation Promotion**: In `ArrivalService.allocate_shortages_for_arrival`, when a shortage is promoted to a future arrival reservation, the new `ArrivalReservation` inherits the creator of the original shortage:
  ```python
  ArrivalReservation.objects.create(
      ...,
      created_by=shortage.created_by
  )
  ```
  Split promoted shortages also retain the original shortage's `created_by` user context.
- **Arrival Reservation -> Stock Reservation Promotion**: In `ArrivalService.finalize_from_movement`, when receiving is completed and an arrival reservation is promoted to physical stock:
  ```python
  StockReservation.objects.create(
      ...,
      created_by=arr_res.created_by
  )
  ```
  This guarantees that the ultimate stock hold preserves the original creator of the commitment.

### 3. UI and Tooltip Enhancements
- Updated list views for Stock Reservations, Arrival Reservations, and Shortages to render the "Created By" user info.
- Updated the interactive Sales Order creation tooltips to include reservation creator details.

## Consequences

### Positive:
- **Consistently Auditable Trail**: Clean tracing of reservation creation from the initial shortage all the way to physical stock hold.
- **Accurate Deletion Tracking**: Soft-deleted reservations now properly log `deleted_by` instead of losing deletion context.
- **Better Diagnostics**: UI cards and tooltips now clarify whether a reservation was generated by the System, a Sales Rep, or a specific Operator.

### Negative:
- **Parameter Overhead**: Requires passing the user context down through various view methods, service calls, and signal receivers.
